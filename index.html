My path through Salesforce followed the usual widening arc: administration and app building first, then declarative and programmatic development, then consulting-grade certifications across the clouds (Sales, Service, CPQ, Experience), and eventually full ownership of architecture, security, and integration for a platform used by over 100,000 people.

Over that time the scope grew from building on Salesforce to being responsible for it — the integrations that keep robot shipment, warranty, and licensing data in sync across systems; the async processing that lets that happen at scale without blocking users; and the access-control and audit-trail decisions that make the platform something compliance can sign off on.

Why Agentforce, and why now

Agentic automation is a natural extension of that governance work, not a departure from it. An AI agent that can write to Salesforce is, from an architecture standpoint, just another caller — and every caller needs the same guardrails: don't duplicate a side effect on retry, don't let bad input reach the database, don't let a large or unusual action execute unsupervised, and don't leave the org in a half-written state if something fails partway through. I've built that pattern for human-facing integrations for years; I'm now building it explicitly for agent-facing ones.

This is an early-career pivot into AI-driven automation grounded in a decade of Salesforce architecture — not a claim of deep AI/ML research experience.

03 · Public Demo — Agentic Entitlement Grant

A generic, from-scratch rebuild of the governance pattern above

Client work isn't public, so I rebuilt the core governance pattern behind the my.kuka.com entitlement system as a standalone, generic SFDX package — no client code, no client data, just the pattern: how to let an agent request a write, and how to make sure that write is safe.

Agentforce Topic / Flow │ ▼ GrantEntitlementAction (@InvocableMethod — Flow & Agentforce entry point) │ ▼ EntitlementService ─────────────────────────────┐ 1. Idempotency check (replay-safe on retry) │ 2. Validation (EntitlementValidator)│ 3. Approval-threshold gate (large requests → │ "Pending Approval", not auto-executed) │ 4. Savepoint / rollback on failure │ │ │ ▼ │ Committed, audited entitlement write ◀───────────┘
The agent only ever sees a typed Request in / Result out — it never touches the object or SOQL directly.

The point isn't the AI call, which is a single @InvocableMethod. The point is everything downstream of it: idempotency so a retried request can't double-grant, validation before anything touches the database, an approval gate so a large or unusual grant gets routed for human review instead of executing unsupervised, and a savepoint/rollback so a failure partway through can't leave the org in an inconsistent state. It ships with a 6-test Apex test class covering grant, duplicate, reject, and approval-routing paths.
